# Сопоставление исправлений с требованиями диплома

Источник: [netology-code/fonecmid-diplom](https://github.com/netology-code/fonecmid-diplom/tree/2d65c44bdd535706075d35b96fbfabf3b540363f), проверенный коммит `2d65c44bdd535706075d35b96fbfabf3b540363f`.
Это проверка текущего решения и исправлений по скриншотам, а не подтверждение выполнения всего диплома.

## Что уточнило ТЗ

Формула отпускных прямо задана в [tasks/hrm.md](https://github.com/netology-code/fonecmid-diplom/blob/2d65c44bdd535706075d35b96fbfabf3b540363f/tasks/hrm.md):

`Начисленная сумма за 12 месяцев / Количество рабочих дней * Календарные дни отпуска`.

Во время отпуска оклад не начисляется. Расчёт должен использовать механизмы сложных периодических расчётов. Предыдущее объяснение в PR, что формула неизвестна, было ошибочным: эти требования есть также в `tasks/hrm.md` пользовательского репозитория. Не хватает реализации и источника рабочих дней в конфигурации, а не формулы в ТЗ. Дополнительного согласования самой формулы не требуется.

Отчёты должны читать регистры, без обращений к документам. Факт анализа актов — только сумма работы специалиста по номенклатуре из константы; абонплата в эту сумму не входит.

## Исправленные после сопоставления пункты

| Пункт ТЗ | Изменения |
|---|---|
| Отчёт только по регистрам | Добавлен оборотный регистр `ВКМ_ВыставленныеАкты`: клиент, договор, номенклатура, сумма. Реализация пишет услуги в регистр при проведении; отмена проведения удаляет движения стандартным механизмом. Существующий регистр Продажи и его учётная логика не изменялись. |
| Фактическая сумма только по работам специалиста | Отчёт использует обороты нового регистра с обязательным отбором по константе `ВКМ_НоменклатураРаботыСпециалиста`. Работы и акты объединяются без размножающего соединения, затем агрегируются по клиенту и договору. |
| Автозаполнение реализации | Очищается таблица Услуги, создаются абонплата и одна суммарная строка работ за месяц. Константы проверяются до очистки. Это заменяет предыдущую правку с выборочным сохранением посторонних услуг и соответствует явному требованию ТЗ. Товары не очищаются. |

В экспортной функции объекта обработки — вызов единого менеджера. Перед проведением вызывается `ПроверитьЗаполнение()`. Защита от повторного создания сохранена. |
| 28 дней суммарно по сотруднику | Подсветка графика использует сумму дней по сотруднику во всех строках документа. Суммы обновляются при изменении таблицы. Пример: две строки по 15 дней подсвечиваются обе. |

UUID существующих в PR объектов сохранены. |

| Программное изменение формы договора | Порядок абонентских полей дополнительно устанавливается методом `ВКМ_УпорядочитьАбонентскиеПоля`. |

## Оставшиеся несоответствия

| Область | Что обнаружено и что ещё требуется |
|---|---|
| Расчёт зарплаты | Денежный расчёт отпускных по формуле ТЗ не реализован. В конфигурации нет источника рабочих дней/графиков, связи графика с регистром расчёта и полноценного вытеснения оклада отпуском. Текущий отказ для неподдержанных начислений — временная защита, а не выполнение ТЗ. Нужна доработка модели и алгоритма периодических расчётов, а затем проверка на платформе. |
| Выработка сотрудника | Нет отдельного регистра `ВыполненныеСотрудникомРаботы`. Сейчас используется клиентская стоимость работ с процентом, применяемым при начислении. По ТЗ вознаграждение сотрудника нужно фиксировать при проведении обслуживания: часы клиента * ставка клиента * действующий процент / 100. Иначе изменение процента может менять результат задним числом. Нужны отдельные движения, адаптация расчёта зарплаты и отчёта выработки. |
| Премии | Документ существует и включён в зарплатную подсистему, но его алгоритм не проверен и не исправлен этим PR. В модуле есть обращение к периодам действия регистров без включённого механизма; поиск пустых видов расчёта проверяется сравнением с Неопределено. Требуется отдельное исправление и проверка зависимостей НДФЛ/взаиморасчётов. |
| Остальные отчёты | Стандартный период исправлен в АнализеАктов. В остальных отчётах надо проверить/доработать параметры периода и источники. В отчёте выработки обнаружено чтение клиентских сумм вместо вознаграждения специалиста, период не передан в виртуальную таблицу. Нельзя считать весь набор отчётов соответствующим ТЗ. |
| Роли и профили БСП | Исправлены конкретные права по скриншотам. Поставляемые профили Специалист, Менеджер, БухгалтерИТФирмы и КадровикРасчетчик не найдены в прикладном коде регистрации профилей. Создание профиля вручную из старой инструкции не заменяет поставляемый профиль. Требуется доработка. |
| Префиксы ранее добавленных объектов | В проекте до этого PR уже были непредварённые префиксом зарплатные документы, регистры, роли и другие объекты. Они включены в служебную подсистему, но массово не переименовывались: это отдельная миграция имён с сохранением UUID и проверкой всех ссылок, включая пользовательскую базу. |
| Изменения форм программно | В договоре программно задан порядок полей, однако само добавление полей ранее было сделано в Form.form. Для буквального выполнения требования о программной доработке формы нужно перенести создание добавленных элементов в серверный код и проверить в EDT. |
| Telegram | В исходниках не найдены требуемые прикладные константы, очередь уведомлений и модуль отправки. В рамках исправления скриншотов этот функционал не добавлялся. Пункт ТЗ не подтверждён. |
| Автотест и эталон | Имеющиеся Vanessa-сценарии не запускались. Старые шаги двух дат отчёта не соответствуют новому стандартному периоду; требуется перезапись в клиенте, запуск полного сценария и обновление числового эталона по корректным данным. |
| Демонстрационная база | Наличие релиза с DT и требуемого наполнения базы этим PR не подтверждено. В окружении нет платформы/демобазы; выгрузка не создавалась. |

## Обновление базы и проверки

Новый регистр не заполняется историческими документами автоматически. До проверки отчёта надо в копии базы загрузить конфигурацию, проверить модули, обновить структуру и контролируемо перепровести нужные реализации. Суммы отчёта сравнить с услугами этих реализаций. Без этого старые акты не попадут в новый регистр.

Новые имена реквизитов начисления и подсистемы сохраняют UUID из первого коммита PR. Если первый вариант PR уже загружен в рабочую базу, обновление необходимо сначала проверить на копии базы; перепроведение без проверки выполнять не следует.

Офлайн-проверки:

- `python tests/check_metadata.py` — структура XML и привязки форм; дополнительно проверяются ссылки типов нового регистра и включение его в регистраторы.
- `python tests/test_act_report.py` — три проверки фактического текста запроса отчёта на SQLite-фикстурах: несколько работ/актов и договоров не перемножаются; договор только с актом присутствует; даты и номенклатура соблюдаются. Это проверка агрегирования, не замена виртуальных таблиц 1С.
- BSL Language Server — синтаксический анализ изменённых модулей; не заменяет проверки 1C:EDT.

PR остаётся черновиком. Полного соответствия дипломному ТЗ и успешного выполнения на платформе пока нет.
